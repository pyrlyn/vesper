# T21. Tabs, splits and windows

Status: not started

Native tabs, split panes and multiple windows on both platforms over the same core handles. Done when a crashed terminal poisons one pane and the rest keep running.

Execution plan (split to fit the budget):

- T21.1 Pane tree and poison state (macOS, `macos/`): a pure value type `PaneTree` in `Sources/ScullKit/PaneTree.swift` (leaf or split of two subtrees, an axis, a focused pane; split, close, focus next and previous, no UI types). `TerminalSession` records `TT_POISONED` and `TT_PANIC` from any call as `isPoisoned`, and `TerminalView` draws a "this terminal crashed" notice instead of the grid for a poisoned session. The pane tree is the same shape the Windows app will lay out as viewports. Verify: Swift tests for split, close and focus order; a test that a poisoned handle leaves sibling sessions answering `TT_OK`, using a `test-hooks` compilation flag on `scull-ffi` that exports `tt_term_test_panic` (not in the header, not in the shipped library) and a `swift test` in `macos/` that builds the library with it.
- T21.2 Panes, tabs and windows on macOS: `Sources/ScullKit/PaneHostView.swift` (an `NSView` that lays the tree out with nested `NSSplitView`s and keeps one `TerminalView` per pane, so a split never restarts a shell; a child exit closes its pane, the last pane closes the window) and a `PaneSurface` representable; the app becomes a `WindowGroup` (native window tabs, one pane tree and one set of sessions per window or tab) with File commands New Window, New Tab, Split Right, Split Down, Close Pane and Next or Previous Pane, routed through the responder chain. `TerminalView` gets only a child-exit callback, per-pane focus (first responder, not key window) and the poison notice; its draw path is untouched because T15 replaces it. Verify: `./gradlew check`, `just test`, the C ABI sanitizer test, the macOS app build, `swift test` in `macos/`; the debug snapshot (`-ScullSplit` with `-ScullHostSnapshot`) shows two panes side by side; a second window and a tab open from the menu.
- T21.3 Windows tabs, splits and windows (T17 delivers the WinUI shell): the same `PaneTree` semantics in C# over `Scull.Core` handles, WinUI `TabView` for tabs and one window per `AppWindow`. One swap chain per window: panes are viewports of that swap chain, not separate swap chains, per AGENTS.md. A poisoned handle poisons one viewport. Split to fit the budget:
  - T21.3.1 Pane tree in `Scull.Core`. Execution plan: (1) `Scull.Core/PaneTree.cs`: `SplitAxis`, `PaneNode` (leaf or split), `PaneTree` with the same split, close, focus and focus-next rules as `PaneTree.swift`, plus `Layout(width, height, divider)` that cuts one pixel surface into a `PaneViewport` per pane (the first pane gets the rounded-down half, nothing overlaps or leaves the surface); (2) `Scull.Core/PaneSet.cs`: a tree with one `Terminal` per pane, so a split never restarts a shell and a poisoned terminal poisons its pane only; (3) `Scull.Core.Tests/PaneTests.cs`: the three Swift pane tests, layout tests, and the poisoned-pane test through `tt_term_test_panic`. Verify: `dotnet test windows/Scull.slnx`, `./gradlew check`.
  - T21.3.2 WinUI wiring in `Scull.App`: `TabView` tabs, one `AppWindow` per window, panes drawn as `PaneTree.Layout` viewports of the window's swap chain (a `Renderer` call per viewport), focus and input routed to the focused pane, a child exit closing its pane, and commands for new tab, new window, split right and down, close pane and next or previous pane. Verify: `dotnet build` of the WinUI app on the Windows runner; by hand on a desktop when someone can.
    Execution plan: (1) `Scull.Render`: `Renderer.Render(view, target, Region?)` draws the grid into a pixel region of any target (the viewport clips, one background quad fills the region), `SwapChainTarget.Clear` paints what shows between panes; (2) `Scull.Core`: `PaneCommands.Match` (Ctrl+Shift+T, N, D, E, W, ] and [), `PaneViewport.Contains` and `PaneTree.PaneAt` for hit testing; (3) `Scull.App`: `TerminalPane` (one terminal's renderer and input state) and a `TerminalWindow` with a `TabView`, one `PaneSet` per tab, all panes of the selected tab redrawn into the window's one swap chain whenever one changes, input to the focused pane, mouse to the pane under the pointer (a drag stays with its pane), a child exit closing its pane and the last pane its tab and the last tab its window, a XAML notice over a poisoned pane only; `App.OpenWindow` for New Window. Verify: `dotnet test windows/Scull.slnx`, `dotnet build` of the WinUI app on the Windows runner (compile-checked here with `dotnet msbuild windows/Scull.App -t:Compile -p:EnableWindowsTargeting=true -p:RuntimeIdentifier=win-x64 -p:WindowsAppSDKSelfContained=false`).
  - T21.3.3 One glyph atlas per window on Windows: panes of a window with the same font family and pixel size (size times scale) share one atlas, so a glyph is rasterised and uploaded once; a pane zoomed to another size gets its own, so a zoom never evicts its neighbours' glyphs or mixes sizes.
    Execution plan: (1) `Scull.Render/GlyphAtlas.cs`: what a renderer kept per font moves into `GlyphAtlas` (the faces, the run shaper and its cache, the sprite canvas, the shelf packer and its texture, the frame counter); renderers acquire and release it, and the last release frees it. Each renderer's frame first touches the shelves every user's rows draw from, under one frame counter, so an eviction never drops a glyph a pane drew or will redraw without rebuilding; a grown atlas has a new generation, and every user rebuilds its rows on its next frame. (2) `GlyphAtlases`: a pool per device keyed by family and pixel size that hands out a live atlas or makes one. `Renderer(device, family, size)` keeps working alone on a private pool; `Renderer(device, atlases, family, size)` shares; `SetFont` swaps atlases and keeps the old one when the family is missing. (3) `Scull.App`: the window holds one pool and hands it to its panes; disposing the panes frees the atlases before the device. There is no device-loss path in the app yet, so an atlas lives and dies with its device. Tests, on WARP on Windows (the atlas needs DirectWrite and a device): two renderers on one atlas rasterise a glyph once, different sizes get different atlases, disposing one user keeps the atlas drawing for the other, and a neighbour's glyphs survive evictions caused by another pane. Verify: `./gradlew check`, `dotnet test windows/Scull.slnx`, CI on Windows (Render tests, `dotnet build` of the WinUI app).
